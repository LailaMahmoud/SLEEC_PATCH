**Critical shared defect: detector errors can look like successful verification.** With a scale-valued measure present, `validate_patched_sleec()` first passes syntax checking, then every detector reports `cannot unpack non-iterable function object`. Nevertheless, the gate returns `valid=True` and an empty concern list. This happened in both snapshots.

The syntax checker calls the full `parse_sleec()`, which mutates module-level state. `process_scalar()` remembers a registered scale name, but subsequent parsing creates a new local type dictionary and skips registering that scale in it. Detector wrappers catch the resulting exception and return `(False, message, [])`. `safe_call()` then reports `success=True`, interpreting that false value as absence of a finding. The caller cannot distinguish successful analysis with no issues from failed analysis.

Relevant code: [syntax/verification gate](../../SLEECpatch/app/services/sleec_patch_workbench_engine.py), [scalar registration](../../sleec/sleecParser.py), [exception wrappers](../../sleec/sleec_api.py), and [detector result conversion](../../SLEECpatch/app/services/sleec_detection_engine.py). The corresponding methods and parser are present in both branches. This defect must be fixed before treating verification counts as evidence of repair correctness.

**Development promotes failed LLM candidates into the verified/ranking path.** After two deliberately unsuccessful syntax retries, an invalid patch returned `verified=True`, `syntax_valid=False`, and `formally_verified=False`. A separate syntactically valid patch that left the concern unresolved also returned `verified=True`. Both reached the ranker and its quality-assessment callback. Main rejected both cases.

Development's final-file builder rejected these two candidates, so the test does **not** show invalid SLEEC being exported. The problem is the inconsistent meaning of verification in candidate lists, ranking and persisted metrics. `_surface_llm_patch()` explicitly sets `verified=True`; `generate_verified_patches()` counts and ranks returned candidates. Store/report paths use that same flag. **Neither implementation reliably carries the full witness into repair generation.** In the timing reproduction the raw diagnostic contains `Start` at time 0, `urgent=True`, and `Act` at time 121. Both branches' concern extraction stops at `Concern is raised`, discarding those trace lines from the selected finding passed to generation. Purpose extraction collapses the diagnostic to `Purpose blocking detected.`; a controlled `c1 exists ...` finding is not extracted at all. Both engines also select the first opposing rule pair when a supplied witness identifies no rule.

Development adds AST-derived references and related-rule metadata, but the generation entry point reduces the selected issue to `issue['value']`; those extra fields are not supplied as authoritative repair inputs. Its AST inventory also calls the stateful full parser, so that code should not be copied unchanged. Both branches need a structured diagnosis contract and a conservative response when the affected rules cannot be established.

**Main's repair semantics are worth retaining; its rendering is not sufficient.** Main's concern implementation preserves response polarity and temporal bounds and can narrow an existing exception that enables a concern. Development's concern parser removes `within` information, and its operators preserve the original response/exception even when that is what makes the concern possible. Conversely, main changes valid `unless {urgent}` into invalid `unless ({urgent})` in a serialization probe and fails to split valid custom identifiers `R1bb` and `policy_safe`. Development preserves the rule text and parses both identifiers. Reference: [main concern operators](https://github.com/LailaMahmoud/SLEEC_PATCH/blob/c75d47e19609a8cfd4b8d99ed5eb311e75750a69/SLEECpatch/app/services/deterministic_repair_engine.py#L101), [development source-preserving helpers](../../SLEECpatch/app/services/deterministic_repair_engine.py).

**Both prompts teach some invalid syntax.** Of three concrete operator examples labelled as correct patches, the measure-specialization and capability-refinement outputs fail the grammar in both branches, even with their vocabulary declared. They include `cookingRiskLevel=high` and `and not humanAssents`, respectively. The grammar requires forms such as `({cookingRiskLevel} = high)` and `(not {humanAssents})`. Development adds useful local examples, a syntax contract and few-shot instructions, but retains these contradictory examples. Also, both patch applicators declare every new measure as Boolean; that cannot correctly represent a new scale-valued measure. Reference: [prompt examples](../../SLEECpatch/app/services/prompts.py), [grammar](../../sleec/sleec-gramar.tx), and `apply_patch_to_text()` in the workbench engine.

**Recommended integration order.**

1. Fix the shared verification boundary first. Separate execution success from issue detection; reject errors, unknown results and incomplete analyses. Make syntax/AST inspection free of solver-state mutations. Reset/isolate solver state for each complete analysis, including exceptional exits, and protect concurrent analyses. Do not cache a failed analysis as a clean result.
2. Preserve structured diagnosis: issue kind and stable identity, affected rule IDs/source nodes, witness events/timestamps/measure values, concern or purpose, and proof references. Carry this object through selection, deterministic repair and LLM prompting. Support `exists`/`while` forms and retain purpose details. Require evidence for target selection rather than selecting an arbitrary opposite pair.
3. Retain main's concern polarity/deadline/exception reasoning and strict acceptance path. Port development's faithful rule preservation, grammar-aware conjunction/negation handling, declared-event guard and general identifier handling. Prefer source-preserving edits or a typed AST renderer, with parser checks on every emitted specification.
4. Keep development's prompt scaffolding and schema-normalization intent, after validating every example against the grammar. Require a typed edit description with target, operation, symbol declarations/types and justification. Have deterministic code render it into SLEEC. Raw model text and prompt instructions alone cannot guarantee syntax.
5. Use separate statuses for generated, syntax-valid, formally-verified and awaiting semantic review. Only completed formal checks that remove the target without regressions enter the verified ranking/export path. Keep rejected proposals available in a separate diagnostic view if desired.
6. Add repeat-call tests for scale-valued specifications and expand the focused reproductions across the actual use cases, including temporal bounds, stacked exceptions, ambiguous witnesses, purpose blocking and cumulative repairs. Use stable issue identities rather than relying only on formatted witness text for regression comparison.

The LLM in both implementations proposes refinements after a formal diagnosis; this review does not demonstrate independent discovery of missing domain requirements. Lexical overlap checks are useful heuristics, but they do not prove preservation of stakeholder meaning. That assessment needs explicit domain expectations and human review in addition to formal checks.
